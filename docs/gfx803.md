# gfx803 (AMD Polaris) vision-encode optimizations

Validated improvements for multimodal (image) inference on gfx803 GPUs
(RX 470/480/570/580, GCN4: no coopmat, no packed fp16, wave64) under the
Vulkan backend with RADV. Reference setup: Qwen3-VL-8B on 6x RX 580 8GB,
one GPU dedicated to the vision tower, 5-GPU layer-split text pipeline.

Every change below was validated end-to-end: real image requests against a
running llama-server, timings from the server response, model output checked
against ground-truth test images, and text prompt processing plus generation
speed confirmed unchanged. Cumulative effect on a 4 MP image request:
**117.2 s -> 30.2 s (3.9x)**; results reproduced on a second vision tower
(Qwen3-Omni-30B).

## Changes

| Commit | Change | Measured effect (4 MP request) |
|---|---|---|
| `f13cc52c1` | Pin `n_kv` to the batch-end value for embd (image) batches (`n_kv_floor`). The kq mask otherwise outgrows its exact-fit allocation on every ubatch; each galloc realloc synchronizes the scheduler and drains the multi-GPU pipeline. | 65.3 s -> 39.9 s (with the reuse fix below) |
| `f13cc52c1` | Skip graph reuse for multi-token ubatches when pipeline-parallel. The reuse path must synchronize before rewriting inputs; rebuilding (~2 ms) rotates the scheduler's input copies and submits async. Reuse still applies to single-token decode. | included above; GPU busy during image-token processing 14-23% -> 62-85% |
| `200bf40f9` | Re-reserve the worst-case pp graph after any embd decode. Image-batch reallocs otherwise replace the startup worst-case reservation with exact-fit sizes, permanently degrading later text batches (597 -> 133 t/s until restart). | text pp stays ~597 t/s after any image traffic; no measurable cost |
| `8dd25b969` | `CLIP_FA_PAD_HEAD=1`: zero-pad q/k/v head size to the next multiple of 16 before flash attention in the clip graph, slice the output back. The scalar FA shader runs ragged head sizes far slower (head 72: 0.80 TFLOPS, head 80: 1.20). Zero pads leave the math unchanged. | 40.2 s -> 30.9 s (encode 31.6 -> 22.4 s) |
| `38b3305cb` | Scalar FA `block_cols = 64` default on GCN for large-batch, large-kv shapes, plus `GGML_VK_FA_{BR,BC,RS,WS,DS,STAGE}` tuning overrides. | encode 22.4 -> 21.6 s |
| `715cdd2f1` | `CLIP_SNAP_PATCHES=1`: snap image resize targets >= 2 MP to 8-patch multiples per side when the patch count does not already divide 64. Non-divisible patch counts select FA's bounds-checked variant, ~2.7x slower at large sizes (62.0 s vs 22.6 s encode at equal area); camera 4:3 shapes almost never divide evenly. Resolution change < 2%. | 4 MP encode 62.0 -> 22.9 s for affected shapes |

## Deployment notes

- Use an **F16 mmproj**, not BF16. gfx803 has no native bf16; the Vulkan
  fallback runs the vision GEMMs at 160-360 GFLOPS vs 1000+ for f16
  (4 MP request: 117.2 s -> 65.3 s from this alone). Q8_0 is no faster
  than F16.
- Set `CLIP_FA_PAD_HEAD=1` and `CLIP_SNAP_PATCHES=1` in the server
  environment; both are opt-in and off by default.
- Warm up after start: one large text prompt (first large decode pays RADV
  pipeline compilation) and one large synthetic image (the first encode
  otherwise pays ~40 s of one-time clip pipeline/buffer cost).
